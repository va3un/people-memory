## Connect, protect and enable

1. Save the public App key and confirm Appendix B setup. Saving/opening settings sends no request. Connect Dropbox starts PKCE S256 with a cryptographically random verifier/state, token_access_type=offline and no App secret. The one-use state/verifier live in IndexedDB deviceSettings, expire after ten minutes, and are checked against the exact redirect and saved App key. Codes are removed from the callback URL before token exchange; the hash router returns to Settings.
2. Authorization leaves uploads paused. Tokens are device-only, unencrypted in this browser, never in URLs/logs/exports or another provider's payloads. Refresh uses a separate cross-tab lock, short-lived access tokens and at most one refresh after 401. Failed refresh requires sign-in without clearing records. A disconnect or changed authorization cannot be undone by a late token response.
3. Before enabling an account, prepare a full local recovery snapshot and download its JSON or use Backup now. Enabling also ensures the snapshot exists, so first sync cannot run before protection is saved. The initial snapshot includes all portable rows/photo bytes/history/tombstones and local view metadata, excludes credentials/settings and remains in IndexedDB. It is a full Phase 6 restore file. Merely downloading it does not reset the verified-backup reminder; use the normal backup read-back flow for that.
4. Read the account ID and disclosure that all local directory data/photos may be sent there. Type SYNC and explicitly enable. Account switches always create a new paused authorization and separate account/App-key namespaces. Existing local records remain intact; there is no automatic wipe or upload to a newly signed-in account. New devices can use About you → Connect Dropbox for recovery to restore the existing Me before creating a different one. Two different active Me IDs pause merge rather than guessing identity.
5. Last successful complete sync changes only after data publication, photo operations and a final revision check succeed. Unsynced counts compare the actual current record hashes with the acknowledged baseline, so edits made during an upload remain pending. Sync now does not turn an unconfigured/paused connection on. Disconnect is local to this device and keeps records, baselines, snapshots and conflicts; revoke the app in Dropbox itself if provider-side authorization must also be removed. Already received uploads/passages cannot be recalled.

## Merge and record preservation

The merge is a plain function over validated portable records and a device-local last-successful baseline. Missing rows are not deletions; union preserves all IDs and explicit tombstones. An empty/missing remote never replaces a nonempty local directory. An empty local directory can download an existing valid remote. No IDs are rewritten and different Me identities are not combined.

Each record has a deterministic content-derived change ID, SHA-256 of canonical record JSON. If only one side differs from the common acknowledged baseline, that side wins even when its clock is behind. If both sides changed, or no common baseline establishes a single-side change, both versions are preserved. Timestamp then the stable change ID determines one active version, identically in either arrival order. Equal timestamps never use random choice. Delete-versus-edit receives the same recovery treatment. Identical rows do not create another conflict.

The losing row and winning row are saved in a local recoverable conflict entry, together with account context and both hashes. The conflict save and merged directory commit share one transaction, so storage failure cannot apply a winner without its recovery copy. Repeated identical conflicts deduplicate by the variant pair. All ordinary tables, including captureBatches, retain their complete current content and deleted rows. Record fields such as IDs, timestamps and source_batch_id stay unchanged unless the user explicitly recovers a version. Device-only settings are never imported/synced. Local last_viewed_at, including nested person snapshots in capture history, is excluded from the wire and preserved locally.

A local edit during download invalidates that plan before writes and causes a bounded fresh merge. A local edit after the local commit or during upload is retained and counted unsynced; completing the old upload cannot overwrite it. The baseline advances only for the acknowledged published snapshot, not whatever a later local read happens to contain.

## Conflict review and recovery

Settings → Review sync conflicts shows both versions, deletion flags and account context. Keep active version archives the notice without deleting the other version. Recover other version requires the current record to still match the recorded active version, validates all references, and writes the selected content with a new timestamp. The replaced active version is itself archived, so recovery does not erase that version. A stale record or unsafe reference pauses recovery and offers a download/manual review. Show archived recovery copies keeps previous alternatives reachable.

Download both versions exports a credential-free conflict JSON, including photo bytes where relevant. This is a recovery artifact, not a full-directory import file. Conflict copies and initial snapshots are device-local and excluded from ordinary directory exports because they are stored with sync bookkeeping, not ordinary records. Download them separately before relying on browser storage. They are never garbage-collected automatically. The normal JSON backup still contains every current directory row/photo/history/tombstone.

For a whole pre-sync restoration, pause/disconnect sync first, download a current full backup, then use the normal Phase 6 JSON preview and guarded merge/replace flow. Replacement still requires a freshly saved/verified safety backup and typed REPLACE. Re-enabling sync later merges with Dropbox again; a missing local row alone never asks other devices to delete it.

## Data and photo publication

`data.json` has strict format `people-memory-sync`, schema 1, and validated tables. Ordinary photo blobs are not inline; the photo rows form a manifest of metadata, tombstones and SHA-256 byte hashes. Unknown/device-only fields, future schema versions, broken references, bad dates, excess sizes/counts, invalid images and incompatible Me identities pause sync. The existing full JSON backup format is unchanged and is not interchangeable with this sync manifest.

The canonical photo path remains `photos/<encoded person id>.jpg`. Retained immutable originals additionally live at `photos/versions/<sha256>.jpg`. The manifest refers to the immutable hash, so another device never mistakes a newly overwritten mirror for an old photo. Original JPEG/PNG bytes and MIME metadata are preserved without lossy recompression; the required .jpg path does not reinterpret a legacy PNG blob. Multiple record IDs/versions and deleted photo rows remain preserved.

A cycle downloads data.json/rev, validates all required remote photos, atomically saves the merged local state/recovery copies, then conditionally uploads the data using update+rev or add-only if missing. strict_conflict is true and autorename false. A revision race re-downloads/re-merges, at most three attempts, without force overwrite. Upload acknowledgements and content hashes are validated. A lost acknowledgement leaves the old baseline and can be resolved on retry without duplicate publication.

Changed/new photo versions are then uploaded add-only. Existing immutable files are hash-checked, never blindly overwritten. The canonical mirror is updated or removed only at its observed revision; its previous bytes are retained before replacement/deletion. Photo deletion propagates a tombstone and removes the current mirror while retaining recovery versions. Unchanged photo bytes are not re-uploaded; range probes plus Dropbox content hashes avoid full repeated downloads when supported. Missing/corrupt required downloads never become empty substitute images or partial local imports.

Dropbox has no transaction spanning data.json and every photo. An interruption after data CAS can leave a manifest awaiting its photo upload. The publisher retains all local bytes and retries; another device without those bytes pauses and keeps its previous valid directory. No complete-sync timestamp is set until photos and the final data revision check succeed. Immutable versions avoid destroying photos still referenced by an earlier manifest. External corruption of a hash-named archive pauses sync rather than overwriting it without review. Retained versions consume free account storage; full-storage errors preserve local data and never offer upgrading or automatic cleanup.

## Foreground/offline behavior and limits

One Web Lock serializes sync across app tabs. Unsupported browsers keep local features and require a current Chrome/Edge browser for sync. Triggers are app open, about five seconds after a real record edit, foreground/focus, online and Sync now. Local viewing and status/token changes do not count as contact edits. Offline skips network quietly, records remain local, and online/foreground retries pending work. Transient failures back off from 30 seconds to at most five minutes; malformed/unsafe content is not polled repeatedly. No background execution after the PWA closes is promised.

Requests use only fixed Dropbox HTTPS origins, header-only access tokens or token-endpoint form bodies, no referrer/cookies/cache, refused redirects and bounded header/body waits. Error bodies and credential values are never shown or logged. Content integrity uses both the manifest's SHA-256 and Dropbox's block content-hash algorithm. Existing backup limits also bound sync: 64 MiB data file, 32 MiB total decoded photos, 4 MiB/photo, 600 pixels/side, 50,000 rows and structural/text limits. Invalid or oversized data stops safely rather than pruning records to fit.
